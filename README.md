# Cleandup —— 内容级重复文件清理工具

本目录原有 4 个文件（`dedup_core.ps1` / `dedup_server.ps1` / `dedup_ui.html` / `dedup_wechat.ps1`）
**未做任何改动**，全部保留。v2 是新增的两个文件：

| 文件 | 作用 |
|---|---|
| `dedup_core.ps1` | 引擎：内容级判重（三级流水线）+ 隔离区 + 计划导出 |
| `dedup.ps1` | 命令行入口 |
| `plan_v2.csv` | 实测生成的清理计划（示例产物） |

## 为什么要改：v1 的判重依据在本机数据上命中率为 0

在 `%USERPROFILE%\Documents\WeChat Files`（174,562 个文件）上实测：

| | v1（按文件名去 (N) 后缀 + 同目录） | v2（内容哈希，跨目录） |
|---|---|---|
| 发现重复组 | **0 组** | **12,385 组** |
| 待处理文件 | 0 | 23,828 个 |
| 可释放空间 | 0 | **10.56 GB** |
| 扫描耗时 | 29.5 秒 | 237 秒 |

v1 命中 0 的原因不是"已经被清理过"，而是它的分组键里带了**同目录**限制，
而真正的重复恰好以三种形态存在：

1. **跨月份目录**：`楚雄州人民检察院…方案_H3C_1126.docx` 同时存在于 `2020-03\` 和 `2020-11\`。
2. **(N) 后缀累加**：`X.pptx` → `X(1)(1).pptx` → `X(1)(1)(2).pptx`；
   v1 的正则 `\s*\(\d+\)$` 只剥掉一层，剥完是 `X(1)(1)`，永远撞不上。
3. **微信给了完全不同的名字**：`090240afe63d970d2c070d18666a0cd2_raw.mp4`
   与 `6d6104ddda92cc7fe4f27dcabee59109_raw.mp4` 字节完全相同（各 609 MB）。

结论：判重依据只能是**内容**，不能是文件名。v2 改成 SHA-256 内容哈希，文件名完全不参与判重。

## 三级流水线（参考 Czkawka / fclones / rmlint 的公开算法）

Czkawka 官方文档对 "By hash" 的描述是三步：**按大小分组 → 读文件头部小片段 prehash → 全量哈希**。
v2 采用同样思路，并针对 Windows/PowerShell 做了实现优化：

```
[1/4] 索引         174,562 个文件                         8.3 s
[2/4] 大小分组     22,572 组 / 131,086 个候选               （大小唯一的 43,476 个直接排除）
[3/4] prehash      读每个候选的头部 32 KB → 幸存 12,385 组 / 36,213 个
[4/4] 全量哈希     只对新读取的 11,487 个文件做全量 SHA-256   222 s
```

关键实现点（实测有 12 倍差距）：

- **复用同一个 SHA256 实例 + 固定缓冲区，不用 MemoryStream**：
  逐文件 `New-Object` 的写法是 0.97 ms/文件，优化后 0.078 ms/文件。这是 485 s → 237 s 的主因。
- **文件 ≤ 头部大小时，头部哈希就是完整哈希**，直接记入 `KnownFull`，第 4 阶段不再重复读。
- **逐块流式读取**，绝不把整个文件读进内存（v1 的哈希函数在大文件上会 OOM 风险）。
- **头部大小可调**：`-HeadKB 32`（默认）。实测 `-HeadKB 4` 会把全量阶段从 11,487 个文件推到 31,737 个，
  总耗时反而没有优势，故默认 32 KB。

## 修正的 bug（v1 里的隐患）

1. **硬链接身份归并的正确性**：只有当"同一 fileIndex 在组内出现 ≥2 次"时才算硬链接。
   若把只出现一次的身份也当成一组，会导致每个文件自成一组、永远查不出重复。
2. **永久删除只校验了前端传的 `confirm=true`**：v2 的 CLI 永久删除必须显式 `-Action Permanent`，
   隔离区还原/清空前会再次校验目标路径确实位于隔离区内（`Test-QuarantineSessionPath2`）。
3. **`Export-DedupPlan2` 引用了不存在的 `$g.keeper.links`**：已补上 keeper 的链接数。

```powershell
# 只预览（不动任何文件）
.\dedup.ps1 -Path "%USERPROFILE%\Documents\WeChat Files" -DryRun

# 预览 + 导出计划 CSV

.\dedup.ps1 -Path "%USERPROFILE%\Documents\WeChat Files" -RestoreQuarantine

```

## 已知边界与风险（务必先读）

- **只按内容判重，不看聊天记录归属**。删掉副本后，指向被删副本的聊天消息可能无法直接打开该文件。
  这是所有同类工具的共有风险，微信官方也公开提示过第三方清理脚本"可能导致原来消息打不开"。
- **默认只做"移入隔离区"，不删除**。确认无副作用后再 `-PurgeQuarantine`。
- **必须关闭微信**，否则占用中的文件会移动/删除失败（会逐条报告，不会中断）。
- `Verify Head` 模式只比头部，速度最快但**可能把头部相同、内容不同的文件误判为重复**，
  仅建议在明确知道数据特征时使用；默认 `Verify Full` 不会误判。
- 文件系统级硬链接会被识别，但**离线虚拟文件（OneDrive/百度网盘占位符）**可能读取失败而跳过。
- 两个 .ps1 **必须保存为 UTF-8 with BOM**。本机 ANSI 代码页是 936，无 BOM 会被
  Windows PowerShell 5.1 按 GBK 解析，中文字符串会破坏引号配对导致解析失败。

## 操作日志（v2 新增，v1 完全缺失）

v1 只做了一件事：把被移动的文件清单写进隔离区内部的 manifest.json。除此之外**没有任何操作记录**：

| 操作 | v1 留下的记录 |
|---|---|
| 扫描 | 无 |
| 永久删除（/api/delete） | **无**（只把统计数字回给浏览器） |
| 移入隔离区 | 仅隔离区的 manifest.json |
| 还原 / 清空隔离区 | **无** |

所以「每次操作为什么导不出日志」的答案是：**当时根本没有写日志的代码**。而且 manifest.json
还会在隔离区被清空或全部还原时**连同目录一起删除**，记录随之消失。

### v2 的日志结构

    <扫描根>\_dedup_logs\
    +-- ops.jsonl                       <- append-only 总账，永不随隔离区清空而丢失
    +-- 20261001_134709-dca023\         <- 每次运行一个目录
    |   +-- plan.csv                    <- 本次扫描的完整清理计划
    |   +-- moved-files.jsonl           <- 逐个文件：原路径 -> 隔离区路径、大小、时间
    |   +-- failed.csv                  <- 失败项（若有）：路径、原因
    +-- ...

ops.jsonl 每行一条 JSON，现有事件类型：

| op | 触发时机 | 关键字段 |
|---|---|---|
| scan | 每次扫描完成（含 -DryRun） | scannedFiles / candidates / preSurvivors / fullHashed / totalGroups / totalVictims / realBytes / headKB / elapsedMs |
| quarantine | 移入隔离区完成 | moved / bytes / failedCount / session / totalVictims |
| quarantine-restore | 还原隔离区 | session / files / bytes / restored / failedCount |
| quarantine-purge | 永久清空隔离区 | session / files / bytes |
| purge-permanent | -Action Permanent 永久删除 | moved / bytes / failedCount |

### 日志设计上的几个刻意选择

- **日志在隔离区之外**（_dedup_logs\），且 -PurgeQuarantine **只删隔离区、不删日志**。
  这样「什么时候清了什么、释放了多少」永远查得到。
- **append-only**：ops.jsonl 只追加、不重写，因此可以直接 -ListOps 或喂给别的工具做时间线分析。
- **每次运行一个独立目录**，opId 贯穿该次运行的扫描与执行记录，便于把「计划」和「实际执行的」对起来。
- **写日志失败绝不影响清理**：所有日志写入都包在 try/catch 里，最多黄字提示。
- **_dedup_logs 与 _dedup_quarantine 都被排除出扫描范围**，日志不会被自己扫到。

所以 GUI 里看到的仍然是 v1 的结果——这就是「明明内容相同却扫不出来」的直接原因。
v2 网页版是新增的一组文件，原来那套一个字节都没改：

| 文件 | 作用 |
|---|---|

- 永久删除要连点两次确认；默认按钮是「移入隔离区」。
- 所有操作写日志到 <扫描根>\_dedup_logs\ops.jsonl（append-only）。

### 已知边界

- 网页版目前只做「后台扫描 + 进度」，进度是阶段级而非逐文件百分比（prehash 阶段按每 500 个文件刷新）。
- -Verify Head 可能把头部相同、内容不同的文件误判为重复；对微信数据建议保持默认 Full。
  实测：把所有候选的头部从 64KB 降到 4KB，全量阶段从 11,487 个文件涨到 31,737 个，说明头部越小越依赖全量哈希兜底。

### 汇总表头（v1 有的都在，另加两项）

| 卡片 | 含义 |
|---|---|
| 重复组 | 内容相同的组数 |
| 待清理文件 | 待删个数；副标题是「已校验 N · 不一致 M」 |

| 扫描耗时 | 含策略与校验级别 |
| 判重流水线 | 候选 / prehash 幸存 / 全量读取 各阶段计数 |

### 筛选条件

| 控件 | 作用 |
|---|---|
| 关键字 | 匹配目录名或文件名（回车或点「筛选」） |
| 最小组可释放 | 只显示该组可释放 >= N 的组（不限 / 1MB / 10MB / 50MB / 100MB / 500MB） |
| 上一页 / 下一页 | 每页 50 组，服务端分页（v1 是后端一次性塞满 DOM） |

实测：2019-03 目录共 32 组；加「≥ 10 MB」后剩 5 组；关键字「0311」剩 1 组（就是那一对 mp3）。

### 三种判重方式的区别（实测，同一个 2019-03 目录）

| 方式 | 先比什么 | 结果 |
|---|---|---|
| v1（任何校验级别） | 先按「同目录 + 去掉一层 (N) 的文件名」分组，再在组内校验 | 0 组 |
| v1 + Verify Hash | 同上，组内做 SHA-256 | 0 组（名字分不到一组，哈希根本没机会执行） |
| v2 + Verify Head | 先按大小分组 -> 比头部 32KB | 32 组 / 47 个 / 122.53 MB（全量读 0 个文件） |
| v2 + Verify Full（默认）| 大小 -> prehash -> 全量 SHA-256 | 32 组 / 47 个 / 122.53 MB（全量读 69 个文件） |

要点：v1 的 SHA-256 不是「更强的校验」，而是「根本执行不到的校验」；v2 的差别才是「先比内容还是先比名字」。
Head 模式更快但有误判风险（头部相同、后文不同），默认 Full 不会误判。
另修一处 Head 模式隐患：若某文件没进 prehash 缓存，原写法会访问 null.Hash 打断整个扫描，现改为退回全量哈希。

### 修掉一个让「扫描」完全没反应的 bug

在把汇总卡片改回 v1 布局时，我在 `renderSummary` 里拼「判重流水线」卡片时**引号不配对**
（字符串前半用单引号、后半改成双引号）。这会让整段 `<script>` 解析失败，于是**所有函数都没注册**，
点扫描自然毫无反应。

教训：数括号个数（`(`/`)`、`{`/`}` 各自相等）**抓不到这种错**。已改用真正的 JS 解析器校验，
并加入 el() 引用的 id 是否都在 HTML 中存在的检查：

    UI JS 语法: OK     （node:vm 解析整段 <script>）
    缺失 id: 无        （el("xxx") 引用的 id 都能在 HTML 里找到）
    未定义函数: 无

### 「头部」是什么意思？16 / 32 / 64 / 128 KB 有什么区别？

判重分三级：先按**文件大小**分组，再做 **prehash**（只读文件最前面的 N KB 算指纹），指纹相同的才做**全量哈希**。
那个 N 就是「头部」大小。界面上已加了即时说明（鼠标悬停也有提示）。

| 头部 | 18 万文件 / 10.5 GB 实测 |
|---|---|
| 4 KB | prehash 快，但进全量阶段的文件从 11,487 涨到 31,737 个；总耗时反而没优势 |
| **32 KB（默认）** | 全量读 11,487 个，整树约 316 秒 |
| 64 KB | 全量读 11,487 个，整树约 237 秒（头部读得更多，全量读得一样） |
| 128 KB | 适合视频/大文件为主的目录；小文件场景会白读 |

**重要：头部大小不影响正确性。** 只要文件的头部指纹相同，就会继续做全量哈希；
头部不同意味着内容必然不同，可以直接排除。所以无论选哪个值，结果都是一样的，
区别只在「读多少字节」和「多少个文件要全量读」。

之所以不直接把头部设成 0（全部全量哈希）：那样要把 131,083 个候选文件整份读完（约几十上百 GB I/O）。
头部预筛的作用就是把绝大多数「大小碰巧相同、内容不同」的文件在 32 KB 内淘汰掉。
